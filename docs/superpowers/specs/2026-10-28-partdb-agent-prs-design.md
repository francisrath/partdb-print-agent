# Upstream Part-DB PRs for direct label printing – design

Status: draft, 2026-10-28. Related: [Part-DB-server#1625](https://github.com/Part-DB/Part-DB-server/issues/1625).

## Why

The maintainer hasn't answered #1625 yet. Instead of more prose, we show three working
draft PRs of increasing size so he can pick one (or none). Printing a label must be
**one click** once set up. The two everyday cases:

1. **Onboarding:** print labels for all existing stock once (hundreds of labels, one batch).
2. **Receiving a shipment:** one or a few parts arrive, get stock added, need a label each.

A matching `pdb-print` PR implements the agent side of PR 2 and PR 3.

## Goals / non-goals / anti-goals

- Goals: one-click print from the label dialog, the "Label ▾" menu, and the parts table
  bulk action; one-click agent setup; generic enough for other agents and printer brands.
- Non-goals: printer drivers in Part-DB, agents shared between users (a lab printer used
  by a team: needs a decision on whose rights render the labels – follow-up), a print-on-save option in the lot form (follow-up
  if the maintainer wants it), pick-by-light or other job types beyond `print` (the
  model allows them, nothing implements them).
- Anti-goals: Part-DB interpreting printer or media data; Part-DB opening connections to
  the user's LAN; automatic re-printing (a stuck job must never print twice); copying any
  Part-DB (AGPL) code into this MIT repo.

## Constraints

- Follow Part-DB's AGENTS.md / CONTRIBUTING.md: PSR-12 + ECS, PHPStan level 5, PHPUnit tests,
  every user-facing string as a translation key in `*.en.xlf` + `translation:touch-catalog`,
  Doctrine migrations for schema changes (MySQL, PostgreSQL, SQLite), `lint:twig`,
  `lint:yaml`, `doctrine:schema:validate`.
- Existing patterns to reuse: `ApiResource` + state processor (`LabelGenerationRequest`),
  job entity with owner and status enum (`BulkInfoProviderImportJob`), permission tree in
  `config/permissions.yaml` with `apiTokenRole`, the `label_system/dropdown_macro`, Stimulus
  controllers in `assets/controllers/pages/`.
- An agent authenticates with an ordinary Part-DB API token, read-only is enough.
- Work locally in `~/git/Part-DB-server` (Docker dev env from DEVELOPMENT.md). Nothing is
  pushed or posted until the user says so.

## PR 1 – "Print" button that hands the label to a local agent

**Setup (once per browser):** the agent's web UI has a "Connect to Part-DB" button that
opens `<part-db>/label/agent#url=<agent url>&key=<pairing key>`. The fragment never reaches
Part-DB's server. The page shows the agent URL and a **Connect** button (a click, so a
foreign link can't silently redirect prints); it saves `{url, key}` in `localStorage`.
The same page shows the current connection, lets you disconnect, and documents the
contract for other agents. Also reachable from Tools.

**Printing:** a Stimulus controller adds a **Print** button next to Download in the label
dialog and a printer icon on each profile in the "Label ▾" menu, both only when the
browser is connected. A click opens a window on
`<agent>/v1/handoff?src&type&ids&profile&ts&sig`, the existing bookmarklet contract:
`sig` = hex HMAC-SHA256 over `src\ntype\nids\nprofile\nts` with the pairing key
(WebCrypto). On plain-http Part-DB (no WebCrypto) it sends unsigned and the agent asks for a
confirmation click. Bulk: the existing table action already opens the dialog with all ids.

The dialog's Print uses the dialog's current profile and ids; an unsaved custom label
(no profile) has no Print button, since the agent fetches by profile.

## PR 2 – server-side print jobs, fetched by agents

**Data model** (namespace `App\Entity\AgentSystem`, names are my call):

- `Agent`: id, uuid (generated by the agent, stable across token renewals), name, owner
  (User, from the token), last_seen_at, version, `printers` (JSON list of
  `{id, name, ...opaque}`, as reported). Unique on (owner, uuid); the token is not stored,
  so renewing or rotating it keeps the agent, its jobs and profile defaults.
- `AgentJob`: id, agent, printer (string id), type (`print`), payload (JSON:
  `profile_id`, `element_type`, `element_ids`), status (`pending`, `claimed`, `done`,
  `failed`, `cancelled`), message, created_by (User), created_at, updated_at.
- `LabelProfile`: optional `default_agent` (FK, SET NULL) + `default_printer` (string).

**Agent API** (`ApiResource` + processors, read-only token suffices):

- `POST /api/agent/heartbeat` `{uuid, name, version, printers}` → upserts the `Agent`
  (owner = the token's user, uuid); returns `{agent_id, poll_seconds}` (PR 3 adds `mercure`).
- `GET /api/agent/jobs` → this agent's `pending` jobs.
- `POST /api/agent/jobs/{id}/claim` → atomic `pending`→`claimed` (conditional UPDATE),
  409 if not pending.
- `POST /api/agent/jobs/{id}/result` `{status: done|failed, message}`.

An agent only ever sees its own jobs, and only its owner can send jobs to it, so the
labels the agent fetches with the owner's token never show the sender more than they
could already read. One click = one job (a whole batch); if it fails part-way, the result
message says so and the agents page offers **Send again** (a new job, same payload) – no
per-label tracking. The job's `printer` wins over the agent's local profile routes; the
agent's media check still applies and fails the job with a clear message on a mismatch.
Printer ids in the heartbeat are the agent's own printer ids. A `claimed` job without a result after 10 min shows
as "unknown" in the UI; it is never re-queued automatically. Finished jobs older than 30
days are pruned on insert.

**Permissions:** new group `print_agents`: `use` (register your agents and send jobs to
them; apiTokenRole READ_ONLY), `manage` (see and delete everyone's agents).

**UI:**

- Tools → "Print agents": your agents, their printers and reported state, last seen,
  recent jobs with status and **Send again**; rename, delete.
- Label profile edit: "Default printer" select (agent printers visible to the editor).
- Label dialog: **Print** sends a job to the profile's default printer, `▾` picks another
  printer (remembered per browser); PR 1's local agent stays as "This computer".
- "Label ▾" menu printer icon and the parts table action **Print labels** (with a profile)
  create the job directly when the profile has a default printer, else open the dialog.
- After sending: flash "Sent N labels to <printer>"; status visible on the agents page.

Shipment case: add stock, then one click on the lot's "Label ▾" printer icon; several parts
→ select them in a parts list → **Print labels**.

## PR 3 – instant delivery via Mercure

- Add `symfony/mercure-bundle`; configured by env (`MERCURE_URL`, `MERCURE_PUBLIC_URL`,
  `MERCURE_JWT_SECRET`), off when unset.
- On job creation, publish a **private** update on `<base>/agents/<id>/jobs`.
- Heartbeat response adds `mercure: {hub, topic, token}` with a short-lived subscriber
  token limited to that topic.
- Fix `Dockerfile-frankenphp`'s Caddyfile to Mercure 1.x syntax (`issuer` block) so the
  built-in hub starts; document the Apache image's sidecar option.
- Polling stays the fallback; the agent re-lists pending jobs after each reconnect.
- Risk to verify first: whether `symfony/mercure` issues tokens Mercure 1.x accepts
  (`at+jwt`, `iss`, `aud`, `authorization_details`). If not, Part-DB signs the token itself.

## `pdb-print` PR (matches PR 2 + 3)

- `serve` gains an agent loop per instance: heartbeat every 30 s with configured printers
  and SNMP state; 404 → feature off (retry hourly), bookmarklet keeps working.
- Jobs: list → claim → existing fetch/render/print path → result (with the SNMP
  confirmation or error text).
- Mercure: SSE subscriber (stdlib, from the POC) when the heartbeat offers it; polling as
  fallback.
- Web UI: "Connect to Part-DB" button (PR 1 setup link).
- Tests with a fake Part-DB on 127.0.0.1, never a real printer.
